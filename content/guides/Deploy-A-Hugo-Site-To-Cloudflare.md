Today I decided to set up a small tech blog using Hugo. I wanted something simple, Markdown files, which are my favourite format these days for all things notes, good SEO, no point having a website if no one can find it and very little maintenance, and automatic deployment whenever I push changes to GitHub.

I settled on the [PaperMod](https://github.com/adityatelange/hugo-PaperMod/wiki/) theme and decided to use GitHub for the repository, with Cloudflare for hosting. PaperMod met all my requirements as far as SEO was concerned, and it looked like a simple theme, which for me means that if I want to make changes, I can without having to kill myself reading documentation.

## Prerequisites

This guide assumes:

- You can get Hugo working on your computer.
- Your Hugo site will be stored in a GitHub repository.
- You have a Cloudflare account.
- Your domain is already using Cloudflare for DNS.

In my case, `vincatech.net` was already managed by Cloudflare, so Cloudflare could configure the DNS for the Worker when I added it as a Custom Domain.

When all is in place the final work flow below should be largely automatic, other than me writing the article and then git push everything else should just work.

```text
Write article
   ↓
git push to Github
 ↓↓↓↓↓↓↓↓ Automatic
Cloudflare
   ↓
Hugo build
   ↓
Cloudflare Worker
   ↓
vincatech.net
```

## Installing Hugo

I'm using Fedora, which already had a recent extended version of Hugo available, the following commands got me started.

```bash
sudo dnf install hugo
hugo version --> hugo v0.162.1+extended linux/amd64
cd ~
hugo new site vincatech
cd vincatech
git init
git submodule add https://github.com/adityatelange/hugo-PaperMod.git themes/PaperMod
rm hugo.toml
nvim hugo.yml
```

```yaml { title = "hugo.yml" }
baseURL: "https://vincatech.net/"
locale: "en-AU"
title: "VincaTech"
theme: "PaperMod"

enableRobotsTXT: true

params:
  env: production
  description: "Tech notes, projects and ideas."
  author: "Vincent"

---- For search ----
outputs:
  home:
    - HTML
    - RSS
    - JSON
```

To check what the state of play is, try the following command -

```bash
hugo server -D
```

The `-D` means development which includes draft articles.

## Organising the Content

I decided on three main types of content:

- **Posts** for dated notes, experiments and ideas.
- **Guides** for information I expect to maintain.
- **Projects** for longer-running projects.

That gives me:

```text
content/
├── posts/
├── guides/
└── projects/
```

I also created separate Hugo archetypes for each. Each article also gets a description and tags, everything gets a creation date, projects and guides get `lastmod` with projects getting `active`, `completed`, `on-hold`.

Below is an example for projects.

```yaml { title = "archtype/projects.md" }
---
title: "{{ replace .File.ContentBaseName `-` ` ` | title }}"
date: {{ .Date }}
lastmod: {{ .Date }}
draft: true
description: ""
tags: []
status: "active"
---

```
A new post, guide or project can now be created with -  

```bash
hugo new content posts/my-new-post.md
hugo new content guides/my-new-guide.md
hugo new content projects/my-new-project.md
```


I decided not to bother with categories. The Posts, Guides and Projects sections already provide the main structure, while tags can describe what the content is actually about.


I was particularly interested in SEO, so I inspected one of the HTML files generated by Hugo.

So there didn't appear to be any need to bolt another SEO system onto the site.

## Putting the Site on GitHub

Once the local site was working, I created a GitHub repository called `vincatech`.

I created a dedicated GitHub SSH key and configured `~/.ssh/config` to use it for `github.com`. I then uploaded the SSH key to GitHub.
The repository remote then became:

```bash
# Create the GitHub SSH key
ssh-keygen -t ed25519 -C "github" -f ~/.ssh/id_ed25519_github

# Test GitHub authentication
ssh -T git@github.com

# Rename the local branch to main
git branch -M main

# Change the existing origin from HTTPS to SSH
git remote add origin git@github.com:Vincat/vincatech.git

# Push and set the upstream
git push -u origin main
```

## Connecting Cloudflare to GitHub

This is where things became more interesting.  
To begin you need to log into your Cloudflare account then go to Computer --> Workers & Pages, click on Create Application, it is there you select GitHub, authorize the connection with read only access to the specific repo for the website.

## First Gotcha: Wrangler Configuration

The Hugo build worked immediately, but deployment failed with:

```text { title = "ERROR"}
A compatibility_date is required when uploading a Worker.
```

The solution was to create `wrangler.jsonc` in the root of the repository:

```json { title = "wrangler.jsonc"}
{
  "name": "vincatech",
  "compatibility_date": "2026-08-24",
  "assets": {
    "directory": "./public/"
  }
}
```

Once that was committed and pushed, Cloudflare rebuilt the site.

This time Wrangler found the 87 generated files, uploaded them and successfully deployed the site.

## Second Custom Domain

Because the Worker itself is hosting the complete static site, `vincatech.net` needed to be configured as a **Custom Domain**.

```text
vincatech.net
```
as the Worker's Custom Domain.

## Third Gotcha: Old DNS

The site still didn't work from my laptop because I had some old DNS records from previous experiments, so before going down this road, I suggest clearing all DNS records.
After removing the old records and allowing Cloudflare to configure the Worker custom domain, the public site started working.

Now take note that sometimes DNS propagation can take up to an hour, so if things don't work initially then maybe it's time to have a break and a cup of tea.


The initial setup had more traps than I expected, particularly because Cloudflare's current Workers workflow differs from many older Hugo and Cloudflare Pages tutorials.

But now that it is configured, publishing should be little more than:

```bash
write article
git add .
git commit -m "Add new post"
git push
```

Cloudflare takes care of everything after that.

For a small technical blog, that's exactly what I wanted: Markdown files on my laptop, the source safely stored in Git, static pages with virtually nothing to maintain, and no web server for me to look after.
